# Keeta Operations Portal — Executive Summary

The Keeta Operations Portal is a local ERP-like prototype for logistics and delivery operations. It brings dashboard-user lifecycle, actual-rider assignments, HR and external rider identities, fleet usage, imports, performance/validity, monthly archive, closing preparation, and finance-input readiness into one traceable workspace. It began as a browser-based operational shell and has evolved through incremental, test-gated prompts. Source: `PROMPT_7_1_FINAL_REPORT.md`, sections “Completed Goals” and “Prompt 8 Readiness”; `PROMPT_8_16_FINAL_REPORT.md`, section “Outcome”.

The central business problem is identity and evidence integrity. A platform Dashboard User/Courier ID may be owned by one person while another rider actually works it. Likewise, a registered vehicle may differ from the vehicle actually used. Performance, validity, archive, monthly closing, and finance staging therefore follow the actual assignment period and preserve owner, actual rider, rider source, registered vehicle, and actual vehicle as separate fields. Source: `PROMPT_8_12_PERFORMANCE_ATTRIBUTION_REPORT.md`, section “Completed”; `PROMPT_8_15_RIDER_PERIOD_SPLIT_REPORT.md`.

The current runtime is deliberately a local prototype: Vanilla JavaScript and HTML, entry file `keeta_operations_portal_starter_v4.html`, Vite UI on port 4173, Node development API `server/devServer.js` on port 4174, and browser-local/API JSON storage. React, Next.js, NestJS, PostgreSQL, production authentication, and deployment are not the current stack. Their absence is an intentional sequencing decision, not a defect. Source: `README.md`, sections “Active runtime” and “Demo scope / current limitations”; repository inspection of `package.json` and `server/devServer.js`.

Prompt 8.16 provides read-only Settlement / Finance Input Staging. It identifies required, available, missing, blocked, and future-required evidence without calculating final payable money, payroll, invoice reconciliation, VAT/ZATCA, or final close. The next planned phase is Prompt 8.17, a payroll/rider-settlement preview foundation; Prompt 9 Shift Scheduler remains separate and must not begin until the operations/closing foundation is safe. Source: `PROMPT_8_16_FINAL_REPORT.md`, sections “Outcome” and “Decision”; project prompt scope.

Private rider names, identity numbers, phone numbers, IBANs, workbook contents, CSV rows, environments, and local database contents must never be copied into handoff reports or Git. Use field names, counts, masked identifiers, or synthetic fixtures. Source: `README.md`, “Demo scope / current limitations”; `PROMPT_8_16_GITHUB_PUBLISH_REPORT.md`.
